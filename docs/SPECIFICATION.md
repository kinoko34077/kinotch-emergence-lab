# KiNoTch. Cross-Repository Emergence Lab — Initial Research Specification

## Status and authority
- This is an initial research scope, not an accepted design for implementation or a command to change other repositories.
- This repository owns cross-repository synergy/emergence **research hypotheses, comparisons, evidence maps, experiments proposed, and research decisions**.
- `kinoko34077/devflow` owns cross-repository development policy, Control Issues and Work Orders. Each subject repository owns its specification, code, implementation and tests. Neither authority is superseded here.
- No duplicate implementation of devflow, Algoram, kinotch-judgment-learning or existing orchestration/integration mechanisms is assumed.

## Objective
Continuously examine the owner's existing and future software/research/creative repositories to identify and evaluate:
1. **Reuse**: same knowledge, implementation, specification or test could be shared with fewer duplicated changes.
2. **Composition**: connecting independent functions creates new usable workflows or products.
3. **Learning feedback**: verified experience in one repository changes the quality of decisions or experiments in another.
4. **Emergence**: interactions create a new capability or operating principle not present in any individual repository.
The target is demonstrable outcomes, not maximizing edges, generic frameworks, uniform repo templates, or integration for its own sake.

## Research method
1. Inventory permitted repositories from live GitHub (do not treat a historical list as permanent). Record for each: function, inputs/outputs, owning authority, implementation maturity, available interface, constraints, and current source reference.
2. Identify shared problems, complementary capabilities, repeated failure patterns, and potentially novel combinations across different domains. Include deliberately non-obvious cross-domain combinations.
3. Create a candidate record with: hypothesis, involved repositories, mechanism of interaction, expected new capability, causal assumptions, non-goals, costs, security/privacy boundary, competing simpler alternatives, prior art within the portfolio, and source links.
4. Label evidence separately: CONFIRMED_CURRENT / SOURCE_STATED / INFERRED / HYPOTHESIS / UNVERIFIED. Do not claim an interface or deployed capability just because a README mentions plans.
5. Evaluate each proposal against independent axes: user/research value, novelty over existing capability, complementarity, cost, coupling and reversibility, data/authority boundary, measurability, and potential to generalize.
6. Design the smallest falsifiable validation (where possible), using read-only evidence or synthetic/test data first. A successful static diagram alone is not a functional integration test.
7. When implementation is explicitly authorized, create a bounded devflow Work Order if multiple repositories must change, and repository-local Issues for each owned implementation. Do not directly implement another repository from this research repository.
8. At each milestone, recheck portfolio purpose and available evidence; continue, change path, split, hold or stop. Avoid inventing follow-up work merely to keep the program running.

## Initial lines of inquiry (hypotheses, not commitments)
- Cross-repository development experience -> structured evidence -> conditionally approved judgment rules -> improved agent decisions, while preserving the existing responsibilities of devflow, execution-coordinator, dev_agent, kinotch-judgment-learning and archival/audit tools.
- Algoram-style composability + existing Runtime/API boundaries -> new workflows without rewriting each provider; actual route/adapter compatibility and safety must be proven.
- Japanese orthography, replacement tooling, IDS glyph display, IME and lyric presentation: preserve original text, reading, glyph and visual layers while exploring interoperable artifacts.
- Music pitch/harmony, microtonal editor, lyric timing, subtitles and MViser: study lossless and timing-aware cross-tool handoff without rounding away pitch semantics.
- Artificial-life/language-model experiments: reuse experimental evidence/measurement protocols while keeping different models' algorithms and hypotheses separate.
- Knowledge/navigation/visual interfaces: cross-resource references and spatial discovery, without merging private content or assuming immature prototypes are complete.
- Game/interactive narrative primitives: explore new experiences arising from combining independently validated presentation and interaction patterns.

## Candidate acceptance
A candidate advances beyond exploratory status only when (a) a concrete non-duplicative outcome is described, (b) required existing interfaces and gaps are substantiated, (c) failure/rollback and ownership boundaries are stated, and (d) an experiment could distinguish synergy from extra maintenance cost. Proposal acceptance is not implementation authorization.

## Initial deliverables
- A source-linked permitted-repository capability map (no excluded repositories).
- A deduplicated set of ranked *conditional* synergy/emergence hypotheses and a record of already-implemented links.
- One or more falsifiable, bounded pilot designs and a decision log on whether each warrants a devflow Work Order.
